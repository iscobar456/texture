# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Texture: a monorepo for writing homework as LaTeX on desktop and pulling in photos of paper/whiteboard work taken on a phone, with the final output being a PDF. Priority platforms: Linux + Android first, macOS + iOS second, Windows if it stays cheap.

## Layout

- `apps/desktop` — Tauri 2 app (Rust shell, vanilla-ts + Vite frontend). CodeMirror 6 editor (stex mode, optional Vim) + PDF.js preview + photo inbox (`src/main.ts`); local-first sync in `src/sync.ts`. Rust commands in `src-tauri/src/lib.rs` own all file access. `compile` runs the bundled `tectonic` sidecar (`bundle.externalBin`; `scripts/fetch-tectonic.mjs` downloads a pinned, SHA-256-checked release into the gitignored `src-tauri/binaries/tectonic-<triple>` before `tauri dev`/`build`, so a bare `cargo build` needs that script run once), falling back to `tectonic` on PATH, then `pdflatex`. Tectonic downloads TeX support files on the first compile and caches them, so the very first compile on a machine needs internet and is slow (about a minute). Linux gets the static musl build; macOS universal builds are `lipo`ed; the macOS sidecar must be signed/notarized with the app. Needs `apps/desktop/.env` (see `.env.example`).
- `apps/mobile` — Flutter app (`supabase_flutter`, `image_picker`). Currently: email/password sign-in, a separate create-account screen (confirm password), a check-your-email screen with resend, forgot/reset password, take/pick photo, upload to the `photos` bucket and insert a pending row, with a per-session upload list and retry. Email confirmation is ON in Supabase, so `signUp` returns no session (and no error for an already-registered email, by design); links return via the `dev.texture.mobile://login-callback/` scheme (`authRedirect` in `lib/supabase.dart`, which must be in the dashboard's Redirect URLs). Code is split into `lib/{main,auth_pages,auth_errors,capture_page,widgets,supabase}.dart`. After picking/taking a photo, `lib/edit_photo_page.dart` lets the user rotate (90° steps) and crop (drag handles) before upload; it is pure Dart (`image` package, processed in an isolate, EXIF baked in, capped at 3000px, re-encoded JPEG) so it needs no native plugin. Not implemented yet: deskew/perspective correction and receiving shared images. `receive_sharing_intent` 1.9 and `image_cropper` 13 were removed because they need compileSdk 37 (Flutter 3.47 defaults to 36 and AGP 9.1 caps at 36; going to 37 also needs AGP 9.2 + Gradle 9.4.1) — pin older versions or upgrade the toolchain when building those features. Config comes from the gitignored `apps/mobile/.env` (see `.env.example`) via `apps/mobile/run.sh`, which wraps `flutter run --dart-define-from-file=.env`.
- `packages/api` — `@texture/api`, the TypeScript client/contract for the desktop app (types for `photos`/`assignments`, inbox listing, download, realtime subscription). The Flutter app cannot import it, so the Supabase schema is the real shared contract; keep both clients in step with `supabase/migrations`.
- `supabase/` — migrations (tables, RLS, private `photos` bucket); no edge functions.

## Commands

- Install: `npm install` at the repo root (npm workspaces: `apps/desktop`, `packages/*`).
- Desktop dev: `npm run tauri dev` from `apps/desktop`. Frontend only: `npm run dev`.
- Desktop build: `npm run tauri build` from `apps/desktop`.
- Releases are split by machine, all attaching to one GitHub release per tag: `scripts/release.sh` (Linux bundles + Android APK; creates the draft release), `scripts/release-macos.sh` (run on a Mac: Apple silicon + Intel DMGs, the Intel one cross-compiled; `--ios` adds an unsigned sideload-only `.ipa`), and the manual Release workflow (Windows only; macOS runners are too costly). macOS builds are ad-hoc signed (`bundle.macOS.signingIdentity: "-"` in `tauri.conf.json`), not notarized, because there is no Apple Developer account; unsigned arm64 apps show "damaged", ad-hoc ones show the normal Gatekeeper warning, and the README documents the Open Anyway steps. With a Developer ID, the `APPLE_SIGNING_IDENTITY`/`APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID` env vars override the config and notarize.
- Mobile (Flutter is at `~/flutter/bin`): `apps/mobile/run.sh [flutter run args]`; `flutter analyze` to lint.

## Architecture notes

- Desktop is unusable until signed in (no local-only mode). Documents (identified by a folder path like `Physics/Week 3/HW 1`) and templates are per-account and local-first: files live in the Tauri app data dir (`<app_data_dir>/<user_id>/<folder>/.../<document>/{main.tex,images/,preview.png,.sync.json}` and `.templates/<name>.tex`; on Linux `~/.local/share/dev.texture.desktop/`) on purpose, so they are not casually editable and cannot desync from the server; PDFs leave the app only via Menu → Export PDF. Everything works offline. All writes go through `write_atomic` (temp file + rename; temp names start with `.`, which listings ignore). If storage outgrows loose files (search, history, richer sync), SQLite behind the same Rust commands is the intended next step. Built-in templates are embedded in Rust and never synced.
- Sync (`src/sync.ts`; tables `documents`/`templates` + bucket `project-files` from migrations 0002-0004). `documents` holds both documents and folders (`kind` column); folders have empty source. Items are matched by a stable `id` (migration 0009: `!<uuid>`, or for rows that predate it the old path), never by path; each local item stores that `id`, the server `updated_at` it last matched (`remote_at`), the `remote_path` the server had then, and a `dirty` flag in `.sync.json`. A local path different from `remote_path` is a rename still to push. Clean + server newer → pull; dirty + server unchanged → conditional push; dirty + server newer → conflict, server version kept as a local `"<path> (conflict)"` document and the local version pushed. The server clock (trigger `touch_document`, which ignores `preview_at`-only updates) is the version, never client clocks.
- Delete/rename/move: a directory is a document iff it holds `main.tex`, otherwise a folder; documents cannot contain other items. Deleting records a tombstone in `<user_dir>/.deleted.json` (for anything with a `remote_at`; it carries the item's `id`, older ones are found by path) and sync soft-deletes the server row (`deleted_at`), conditional on the deleted version. A server tombstone removes clean local copies, but an edited, renamed or never-synced local copy wins and restores the row. Rename and move are the same op (`move_item`, `rename_template` for templates): the directory moves with its identity and sync state, `remote_path` is stamped first, and the next sync does an UPDATE of the row's `path` (a folder rename updates each descendant row; ids and storage keys do not change, so no images are re-uploaded). A rename made on another device is applied with `rename_local` (tolerates the target folder already existing). Folders are synced before documents so a renamed folder moves as a whole. Both renamed on two devices: the one that syncs last wins. Rename vs edit elsewhere: the edit is kept (a "(conflict)" copy of the server's version appears), the rename stands. `documents`/`templates` have PK `(user_id, id)` and a unique index on live `(user_id, path)`; images and previews live under `<uid>/<id>/` (templates `<uid>/.templates/<id>/`), so legacy rows keep their old path-shaped keys.
- Previews: `preview.png` (page 1 of the last compile) syncs via storage at `<uid>/<path>/preview.png`; `documents.preview_at` is an opaque marker compared for equality only. Images sync for the open document and for documents pulled or newly pushed in a pass. Templates sync and delete the same way (tombstone kind `template`); built-ins can be overridden by saving a template with the same name, and deleting the override reveals the built-in again. A template is edited in the main editor (`templateName` set, saves via `save_template`, compiles in `.scratch`).

- Phone → desktop flow: the phone uploads to the private `photos` bucket at `<user_id>/<file>` and inserts a `photos` row with `status = 'pending'`. The desktop subscribes to realtime changes to `photos` (`onInboxChange`, which also covers deletes), downloads the image, and marks the row `imported`. Storage RLS depends on that `<user_id>/` path prefix.
- OCR-to-LaTeX runs on the desktop with the user's own Anthropic API key (Settings → Photo OCR). The key is saved by Rust in `<user_dir>/.api_key` (owner-only, device-local, never synced, never returned to the webview); `ocr_image` in `lib.rs` shrinks nothing itself — the webview downscales the photo to ≤1568px JPEG first — and calls api.anthropic.com with effort `low` (thinking tokens are billed as output). Models are an allowlist (`OCR_MODELS` in `lib.rs` and `settings.ts`, keep in step; prices in `settings.ts` are currently unused (the cost line was removed from the OCR dialog)). The result is inserted at the cursor for review, never auto-compiled. Transcriptions are cached in `photos.ocr_latex` (synced with the photo, edits included): reopening Transcribe shows the saved text without calling the API, and only "Transcribe again" is billed.
- Realtime only works while an app is foregrounded. Background push on mobile would need FCM/APNs.
- Keep all backend access behind `packages/api` (desktop) so the backend can be swapped (e.g. PocketBase) later.
- User settings (`apps/desktop/src/settings.ts`: theme, editor color scheme (palettes are CSS variable blocks keyed by `data-editor-theme`; `--cm-line` must stay translucent or it hides the selection), editing mode, font size, wrap, line numbers, auto-compile, default template) are per-device in `localStorage` under `texture:settings`, not synced. Theme works by setting `data-theme` on `<html>`; with none set, CSS follows the OS.
- Snippets/autocomplete are entirely user-defined. The user owns one TOML file (`snippets`, stored at `<user_dir>/.config/snippets.toml`, synced via the `user_files` table / sync kind `config`). `src/default-snippets.toml` is only what a fresh account is seeded with (plus any snippets from the old per-device form editor, migrated once from `localStorage` `texture:snippets`). `src/snippets.ts` parses and validates it (smol-toml; errors listed, last good config stays active), compiles it to completion options and key bindings, and builds the browse list; `src/completions.ts` is only machinery (`latexSource` decides what to suggest from the text before the cursor; `\begin{`/`\usepackage{` contexts read environments/packages from the file; `\ref{` labels are scraped from the document and are the one built-in). Backslash entries are only offered once a backslash is typed. The file is edited in the main editor as a third edit target (`snippetsOpen`, TOML highlighting, saves via `save_config`, Ctrl+Enter validates/applies); user snippet shortcuts live in `snippetSlot` at highest precedence ahead of `vim()` and are disabled while editing the file. Reset replaces the file with the default; there is no backup. While the file is open, a bar above the editor (`#snip-bar`) offers Back (returns to the document or template that was open, remembered in `snippetsReturn`), View original (opens `default-snippets.toml` on GitHub via the opener plugin) and Restore to default (the same confirm dialog as Reset).
- Keyboard shortcuts dialog (`apps/desktop/src/shortcuts.ts`, Menu → Keyboard shortcuts): the built-in list is hand-written because CodeMirror bindings have no descriptions and their command names are mangled in production builds. When you add or change a binding, update it there. Only the user-snippet shortcuts and the Vim on/off note are read live.
- The Snippets dialog (`snippets-ui.ts`) is a searchable browser of whatever the active snippets file defines, plus Edit file / Reset to defaults. There is no form editor.
- Pane layout (`apps/desktop/src/layout.ts`): the editor/preview boundary is a draggable, keyboard-adjustable splitter (fraction stored per device in `localStorage` `texture:layout`, applied through the `--cols` grid variable on `<main>`), and the photo inbox collapses to a narrow rail showing a photo icon with the pending-count badge on its corner (header and section chevrons are inline SVGs, not native `<details>` markers; all card buttons share one neutral style).
- The preview has a full-screen button (`layout.ts`): `#preview.full` is `position: fixed` over the window and the Tauri window is also set to full screen (capabilities `core:window:allow-set-fullscreen` / `allow-is-fullscreen`); Esc leaves both, unless a dialog is open. Each pane is pinned to its grid column in CSS so taking the preview out of flow does not reshuffle the others.
- Compile status lives in a bar along the bottom of the preview (`#compile-bar`, state in `main.ts`: idle / compiling / ok / failed, plus an "edited since" flag set on every edit and cleared when a compile or snippets-apply finishes). A manual compile failure shows the log immediately; an automatic one (`quiet`) only reports failure with a Show log link. There is no header status line any more: one-off notices (export result, sync conflicts, inbox errors) go through `status()` in `main.ts`, which shows a toast.
- Sync status UI (`apps/desktop/src/sync-ui.ts`): the header chip shows one of synced-at / syncing / N changes waiting / offline / problem, and opens a panel (last success, pending items grouped by kind, per-item errors, conflict copies, Sync now). "Pending" is read from local state only (`collectPending`: dirty flags, preview_dirty, new folders, deletion tombstones) and recomputed from `syncSoon()` and after each pass; images and inbox photos are not listed. `doSync()` shares one in-flight pass between callers. On window close (`onCloseRequested` in `main.ts`) the app saves, runs up to two passes with an 8 s cap, then destroys the window; the closing dialog has a Quit now button, and unfinished work stays safe locally.
- Header/UI chrome: `button, input, select, textarea { font: inherit }` and a 14px base are deliberate (controls otherwise fall back to a smaller platform font and mismatch the dropdowns); `.hbtn` is the shared header button, `--surface/--hover/--press/--border` the shared chrome colors. The menu is keyboard operable (arrows, Home/End, type-ahead, Escape returns focus to the button); shortcut hints in it come from `kbd[data-key]` through `showKey`. The document button is a breadcrumb (`setDocLabel`). Ctrl/Cmd+P opens the quick switcher (`switcher.ts`: subsequence fuzzy match, recents from `localStorage` `texture:recent:<user>`, a Create row when nothing matches exactly) and Ctrl/Cmd+, opens Settings; both are captured at the document level before the editor, so they shadow Vim's Ctrl-P.
- Dialogs share one look and one behavior. Look: the base `dialog` rule in `styles.css` (surface, border, shadow, backdrop), `.dlg-head` panel headers with an `.icon-btn` ×, form dialogs padded through `dialog > form` (dialogs themselves have NO padding on purpose), shared secondary/primary(`button[value="ok"]`, `.primary`)/danger button styles and field styles; the button selector lists in that block name specific ids, so a new dialog button needs adding there or to a `.row`. Behavior is in `dialogs.ts` (`initDialogs`, runs over every static `<dialog>`): Esc closes (a ⋮ menu open inside is dismissed first), a click that both starts and ends outside the dialog's box closes it (so scrollbars and drag-selections don't), `data-persistent` dialogs (the exit-sync one) ignore both, and focus returns to the editor when the last dialog closes. Dialogs must be present in `index.html` at load for this to attach.
- Compiling: opening a document starts a quiet compile (`openDocument` → `compile(true)`). `compile` fixes the target (path, scratch) when it starts and drops the result if `viewEpoch` changed meanwhile (the editor moved to another document/template/snippets file), so a slow compile can't paint into, or save a preview for, the wrong document. A compile requested while another runs is queued (one follow-up, manual if any request was manual) instead of dropped. `save_preview` skips identical images so re-compiling an unchanged document uploads nothing.
- Template thumbnails: `<templates dir>/<name>.preview.png`, built lazily one at a time while the picker's Templates tab is open (`buildMissingThumbs` → `compile_template_preview`, compiled in its own `.scratch-thumbs` folder so it never collides with the editor's `.scratch`), refreshed whenever a template is compiled in the editor, and deleted whenever the template text changes (`save_template`, a pulled update, delete) — the sync marker `preview_at` is deliberately kept then, so a stale server image is not re-downloaded. They sync exactly like document previews (`preview_at` marker column on `templates`, file at `<uid>/.templates/<name>/preview.png`, migration 0006; built-in templates stay local). Documents still show a source snippet until they have been compiled or synced to this device.
- The document picker is one dialog with Documents and Templates tabs (`setPickerTab` / `openPicker` in `main.ts`). It opens on the tab for what you are editing, and only highlights a card as current when that kind is open. Menu → Templates… opens it on the Templates tab; there is no separate template dialog.
- Photo inbox (`apps/desktop/src/inbox.ts`, wired in `main.ts` via `initInbox` with injected deps): newest first; full-size originals are cached in memory per session and small thumbnails are generated once per photo (a refresh no longer re-downloads). Cards are Insert / Transcribe (Move to inbox / Transcribe in Used; Restore / Delete forever in Trash); clicking the photo views it larger and the checkbox + toolbar trash it. Insert and Transcribe never use a hidden cursor: they start place mode (`apps/desktop/src/placement.ts`, wired via `pickInsertPoint`/`insertAt` deps), where a marker line snaps to line boundaries (top half of a line = above, bottom half = below; ↑/↓ + Enter or click; Esc cancels; the viewer closes first so the editor is visible). OCR picks the spot before the dialog opens, so cancelling costs nothing, and the position is stored as an offset until Insert. Cards are also draggable onto the editor (`PHOTO_MIME` payload; the window sets `dragDropEnabled: false` so webview drag-and-drop works on Windows). `insertAt` in `main.ts` scrolls to the insertion and shows an Undo toast. Clicking a photo opens the viewer dialog (rotate, zoom, pan, prev/next; rotation is applied by re-rendering through a canvas, and only when you insert or OCR rotated, so unrotated inserts are the untouched original unless the JPEG has an EXIF orientation tag, which is baked in because LaTeX ignores it). Transcribe opens a review dialog: photo on the left, editable LaTeX on the right, optional "also insert the photo"; nothing reaches the document until Insert, and a result that returns after the dialog was closed is ignored (the API call still bills). The inbox width is draggable via a second splitter (`layout.ts`, 200–520px, per device). Popup menus (`popup.ts`: `attachMenu`/`kebab`) attach to `document.body` outside dialogs.
- Format (Menu → Format document, Ctrl/Cmd+Shift+F, Vim `:fmt`): the `tex-fmt` crate (pinned `=0.5.7`, used as a library) behind the `format_tex` command in `lib.rs`. Settings → Format document sets indent (2/4 spaces or tabs) and whether/where to break long lines (off by default); they become a small tex-fmt config string. tex-fmt reports unbalanced `\begin/\end` or braces only as indentation warnings, so `format_tex` matches `ndent` in warning text and refuses (that is why the version is pinned). tex-fmt also indents after every `(` and `[`, which breaks on prose like `\item[ii)]`, `a)` or `[0,1)`, so `protect_delimiters` swaps those (and escaped `\{ \}`, `\\[2pt]`) for private-use stand-ins before formatting and back after, keeping only braces, environments and `\[ \]`/`\( \)` as nesting; it also catches panics, which needs `panic = "unwind"` in the release profile (not `abort`). `format.ts` only asks for the formatted text and turns the difference into minimal line edits (a line diff), so the cursor stays on its text and it is one undo step. `format_tex` has unit tests (`cargo test format_`); the diff was checked with a throwaway randomized script. Sync has a JS test suite (`npm test` in `apps/desktop`, vitest, `src/sync.test.ts`): the real `sync.ts` against in-memory fakes of the Tauri commands and of the server, so keep those fakes in step with `lib.rs` and migration 0009 when sync semantics change. Rust: `cargo test` (`sync_tests`).
- Inbox states (migration 0007): photos are `pending` → `imported` (kept, shown under "Recently used" so they can be inserted again) or `trashed` (undoable delete: `trashPhoto`/`restorePhoto`; the desktop purges anything trashed over 7 days when the inbox first loads each session; "Delete forever" is the only hard delete). Used/Trash queries degrade to empty if the migration is missing so pending photos always show. Images: `thumb_get/put/prune` keep small JPEG previews in `<user_dir>/.cache/inbox/` (cache only, never synced); previews load lazily via an IntersectionObserver with 3 at a time; full-size originals download only when the viewer/insert/OCR needs one and the last 4 are kept in memory. A toast announces photos that arrive while the app is open (`toast.ts`: top-layer popover so it shows over dialogs, but its action button is dropped while a modal is open because a modal makes everything outside it unclickable). Every card has a checkbox; ticking one reveals that list's toolbar (`bar()` in `inbox.ts`) with Select all/none, Move to trash (solid red, undo toast) or, in Trash, Restore / Delete forever, and Cancel. Once something is ticked, clicking a card ticks it too, and ticking in another list starts over. Ticking updates in place so thumbnails don't reload. Trash also always has Empty trash. Pending photos can be reordered (grip on each card: press and drag, or ↑/↓ when focused; this is pointer-event based (`startReorder`), not HTML5 drag-and-drop, which misbehaved in the webview; `movePhoto` updates the DOM in place and the order is stored per device in `localStorage` `texture:inbox-order:<user>`, with new arrivals on top; syncing it would need a `sort_order` column). The OCR button in the selection toolbar (`openBatchOcr`, dialog `obatch-dialog`) picks one insertion point, then shows one review row per selected photo in list order: saved transcriptions are free, the rest are billed only after pressing Transcribe (3 at a time, per-row retry), and Insert places everything as a single insertion (one Undo), optionally with each image above its text. Permanent deletes use a two-click confirm button instead of a dialog. They go through the batch `trashPhotos`/`restorePhotos`/`deletePhotos` in `packages/api`, and `refresh()` coalesces overlapping calls because a bulk change fires one realtime event per row. The sidebar shows one list at a time through Inbox / Used / Trash tabs (`#inbox-tabs`, counts on each; switching clears the selection); "Recently used" in this note is the Used tab. Used photos have Move to inbox (card button and toolbar action) instead of Insert, via `restorePhotos`.
